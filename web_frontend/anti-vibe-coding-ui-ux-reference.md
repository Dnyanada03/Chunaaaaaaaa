# Anti-Vibe-Coding UI/UX Design Reference

## Purpose

Use this document as a **design-quality reference for refining the
existing website**.

The objective is **not** to make the website less modern. The objective
is to make it feel like a **real, mature, thoughtfully designed
product** rather than an AI-generated landing page or generic
"vibe-coded" concept.

> **Core principle:** Prefer intentional design, real product
> information, usability, and credibility over decoration.

------------------------------------------------------------------------

# 1. Design Philosophy

The final website should feel:

-   Intentional
-   Product-focused
-   Credible
-   Specific
-   Human-designed
-   Mature
-   Usable
-   Visually consistent
-   Fast and responsive

It should **not** feel:

-   AI-generated
-   Template-like
-   Over-designed
-   Dribbble-shot-like
-   Generic SaaS
-   Excessively animated
-   Neon/glowy for no reason
-   Full of decorative cards
-   Like a collection of random UI trends

### Decision Rule

Whenever there is a choice between:

**Decoration vs. meaningful information → choose meaningful
information.**

**Visual effect vs. usability → choose usability.**

**Generic marketing copy vs. specific product information → choose
specific information.**

**Another card vs. a real product demonstration → choose the product
demonstration.**

**Unnecessary animation vs. performance → choose performance.**

------------------------------------------------------------------------

# 2. Anti-Pattern Checklist

The following patterns commonly make websites look "vibe coded." Audit
the existing website and remove or redesign them where they do not have
a genuine purpose.

## 2.1 Harsh Gradients

### Avoid

-   Large aggressive gradients
-   Multiple unrelated gradients
-   Neon gradient backgrounds
-   Gradient text used everywhere

### Prefer

-   Solid surfaces
-   Subtle tonal transitions
-   Restrained gradients used only when they support the brand

------------------------------------------------------------------------

## 2.2 Excessive Icon Usage

### Avoid

Repeated:

> Icon → Heading → Paragraph

for every feature.

Do not put an icon beside every sentence simply because an icon library
is available.

### Prefer

Use icons only when they: - Communicate an action - Improve
recognition - Represent a meaningful concept - Support navigation

------------------------------------------------------------------------

## 2.3 Pure White Everything

A completely white interface can feel unfinished when every section has
identical visual treatment.

### Prefer

Create hierarchy using: - Surface variation - Borders - Typography -
Spacing - Section backgrounds - Content density

Do not introduce random colors just to solve this.

------------------------------------------------------------------------

## 2.4 Rainbow UI

### Avoid

Giving every feature/card a different bright color.

### Prefer

Define a clear palette:

-   Primary
-   Secondary
-   Neutral
-   Success
-   Warning
-   Error

Color should have **meaning**, not merely decoration.

------------------------------------------------------------------------

## 2.5 Excessive Drop Shadows

### Avoid

Putting large shadows on: - Cards - Buttons - Images - Inputs - Modals -
Every section

### Prefer

Use: - Borders - Surface contrast - Spacing - Subtle elevation

A shadow should communicate depth or layering.

------------------------------------------------------------------------

## 2.6 The "Three Cards in a Row" Problem

Do not automatically convert every feature into three cards.

### Prefer layouts based on content:

-   Two-column explanations
-   Product screenshots
-   Timelines
-   Tables
-   Comparison layouts
-   Editorial sections
-   Asymmetric compositions
-   Full-width demonstrations
-   Step-by-step workflows

**Content determines layout.**

------------------------------------------------------------------------

## 2.7 Emoji Overuse

Avoid using emojis as a substitute for visual design.

Emojis may be appropriate for informal products, but should not become
the primary visual language of a professional interface.

------------------------------------------------------------------------

## 2.8 Excessive Glassmorphism

### Avoid

-   Blurred glass cards everywhere
-   Transparent surfaces everywhere
-   Excessive backdrop blur
-   Glowing borders
-   "Liquid glass" applied indiscriminately

### Prefer

Use glass effects only when they are genuinely appropriate to the visual
identity.

------------------------------------------------------------------------

# 3. Typography

Typography is one of the strongest ways to make a website feel
professionally designed.

## Avoid

-   Excessive giant headings
-   Too many font weights
-   Random font combinations
-   Extremely tight line heights
-   Text used only as decoration
-   Every section having a huge headline

## Prefer

Establish a clear hierarchy:

1.  Display / Hero
2.  Page heading
3.  Section heading
4.  Subheading
5.  Body
6.  Supporting text
7.  Metadata

Use consistent:

-   Font family
-   Font weights
-   Font sizes
-   Line heights
-   Letter spacing

Typography should make the content easier to scan.

------------------------------------------------------------------------

# 4. Marketing Copy

Avoid generic AI-generated marketing language.

## Avoid phrases such as:

-   "Revolutionize your workflow"
-   "Unlock your potential"
-   "The future of..."
-   "Built for modern teams"
-   "Transform the way you..."
-   "Next-generation..."
-   "Seamlessly..."
-   "Supercharge your..."

unless they are genuinely relevant and supported by the product.

## Avoid the "It's not X, it's Y" formula

This pattern is heavily associated with AI-generated marketing copy.

### Prefer

Explain:

-   What the product does
-   Who it is for
-   What problem it solves
-   How it works
-   Why it is useful
-   What makes it different

Be specific rather than dramatic.

------------------------------------------------------------------------

# 5. Feature Sections

## Avoid

Repeated sections containing:

-   Icon
-   Short heading
-   Two-line description
-   Decorative card

## Prefer

Show the actual product.

For example:

-   Real screenshots
-   Workflow demonstrations
-   Data visualizations
-   Product interactions
-   Before/after examples
-   Process diagrams
-   Actual outputs
-   Realistic sample data

### Rule

> **Show, don't merely describe.**

A real product screenshot is usually more convincing than five
decorative cards.

------------------------------------------------------------------------

# 6. Bento Grids

Bento grids can be useful, but should not become the default layout.

## Use when

-   Different content types need different sizes
-   A dashboard-like overview is appropriate
-   The product naturally has modular information

## Avoid when

The bento grid exists only because it is currently trendy.

------------------------------------------------------------------------

# 7. Cards

Cards should represent meaningful conceptual boundaries.

A card should answer:

> "Why is this information grouped together?"

If there is no good answer, the card may not be necessary.

### Avoid

-   Excessive rounded cards
-   Every sentence inside a card
-   Cards inside cards
-   Multiple decorative cards with identical structure

### Prefer

-   Strong grouping
-   Clear hierarchy
-   Appropriate borders
-   Appropriate spacing
-   Minimal decoration

------------------------------------------------------------------------

# 8. Border Radius

Not everything needs a huge radius.

### Avoid

-   Every element being a pill
-   Huge rounded rectangles everywhere
-   Buttons, cards, inputs and containers all having identical radius

### Prefer

Use a small, consistent radius system based on component type.

Example:

-   Small radius → controls
-   Medium radius → cards
-   Larger radius → major surfaces only

The exact values should follow the existing design system.

------------------------------------------------------------------------

# 9. Color System

Do not automatically default to:

> Purple + Black + Neon Gradient

This has become a common AI/SaaS visual pattern.

Likewise, avoid randomly assigning pastel colors to different cards.

### Prefer

Choose colors based on:

-   Brand identity
-   Product purpose
-   Accessibility
-   Semantic meaning
-   Content hierarchy

Use accent colors deliberately.

------------------------------------------------------------------------

# 10. Decorative Effects

Avoid decorative elements that do not contribute to understanding.

### Remove or minimize:

-   Random radial orbs
-   Floating blobs
-   Dot grids
-   Sparkle icons
-   Excessive glows
-   Random particles
-   Decorative code windows
-   Floating gradients

These should exist only if they have a genuine relationship with the
product or brand.

------------------------------------------------------------------------

# 11. Animations

Animation should communicate something.

## Good animation

-   Page transitions
-   Loading states
-   Expand/collapse
-   Drag interactions
-   Progress
-   Feedback
-   Hover affordances
-   State changes

## Bad animation

-   Every button moving
-   Every arrow sliding
-   Cards constantly floating
-   Random glowing effects
-   Excessive parallax
-   Animation added simply to impress

### Rule

> If removing the animation does not reduce usability or understanding,
> question whether it needs to exist.

------------------------------------------------------------------------

# 12. Hover States

Hover interactions should be subtle.

### Prefer

-   Slight surface change
-   Border change
-   Small elevation change
-   Clear cursor/interaction feedback

### Avoid

-   Dramatic scaling
-   Large movement
-   Excessive glow
-   Rotation
-   Flashing
-   Large color transformations

------------------------------------------------------------------------

# 13. Loading States

Real products need real states.

Where asynchronous content exists, implement appropriate:

-   Skeleton loaders
-   Loading indicators
-   Empty states
-   Error states
-   Retry actions

Do not create fake loading animations purely as decoration.

------------------------------------------------------------------------

# 14. Empty States

A real application will sometimes have no data.

Create useful empty states containing:

1.  What is currently empty
2.  Why it may be empty
3.  What the user can do next

Avoid empty screens with only a decorative illustration.

------------------------------------------------------------------------

# 15. Error States

Errors should be understandable.

Provide:

-   Clear explanation
-   Appropriate recovery action
-   Retry where applicable
-   Useful context

Avoid technical errors being shown directly to users unless they are
useful.

------------------------------------------------------------------------

# 16. Product Credibility

Never fabricate:

-   Testimonials
-   Customer names
-   Company logos
-   User counts
-   Revenue figures
-   Reviews
-   Awards
-   Partnerships
-   Performance claims

If real information is unavailable:

-   Remove the section, or
-   Use clearly marked placeholders

Never make fictional information appear real.

------------------------------------------------------------------------

# 17. Pricing

Do not automatically create three pricing tiers.

Only include pricing if the actual product requires it.

Never invent:

-   Prices
-   Discounts
-   Plans
-   Features
-   Billing claims

If pricing information is unavailable, structure the page so real
pricing can be inserted later.

------------------------------------------------------------------------

# 18. Legal and Trust Elements

For a real product, include appropriate areas for:

-   Terms of Service
-   Privacy Policy
-   Contact/support
-   Cookie information where applicable
-   Company information where applicable

### Important

Do not generate fake legal policies and present them as authoritative.

If actual legal information is unavailable, use clearly marked
placeholders.

------------------------------------------------------------------------

# 19. Navigation

Navigation should represent the actual information architecture.

### Avoid

Large navbars filled with unnecessary links simply to look
sophisticated.

### Prefer

A small number of meaningful destinations.

Navigation should answer:

> "Where does the user actually need to go?"

------------------------------------------------------------------------

# 20. Buttons and CTAs

Every button should have a clear purpose.

Avoid vague CTAs when a more specific action is possible.

### Instead of

"Explore"

consider:

-   "View Dashboard"
-   "Create Project"
-   "Start Analysis"
-   "Download Report"
-   "Contact Team"

depending on the actual functionality.

### Primary CTA

There should generally be one visually dominant action per major
context.

------------------------------------------------------------------------

# 21. Realistic Information Density

AI-generated interfaces often have:

-   Huge empty spaces
-   Very little meaningful content
-   Large headings
-   Three tiny cards
-   Decorative elements filling the remaining space

Real products usually contain useful information.

### Prefer

Realistic density with:

-   Meaningful content
-   Clear hierarchy
-   Supporting information
-   Useful controls
-   Actual product output

Do not fill empty space with decoration merely to make a page longer.

------------------------------------------------------------------------

# 22. Real Product Demonstration

This is one of the highest-priority improvements.

Whenever possible, demonstrate the actual product through:

-   Screenshots
-   Interactive previews
-   Realistic mock data
-   Workflow demonstrations
-   Charts
-   Tables
-   Before/after examples
-   Actual UI states

The visitor should be able to understand:

> **What does this product actually do?**

within a few seconds.

------------------------------------------------------------------------

# 23. Responsive Design

Do not simply stack desktop elements on mobile.

For mobile:

-   Reconsider hierarchy
-   Simplify navigation
-   Adjust typography
-   Reduce unnecessary decoration
-   Preserve important actions
-   Maintain readable spacing
-   Ensure touch targets are usable

The mobile experience should feel designed, not compressed.

------------------------------------------------------------------------

# 24. Accessibility

Ensure:

-   Adequate color contrast
-   Visible focus states
-   Keyboard navigation
-   Semantic HTML
-   Accessible buttons
-   Accessible form labels
-   Readable font sizes
-   Meaningful alt text
-   Reduced-motion support where appropriate

Accessibility is part of professional product design.

------------------------------------------------------------------------

# 25. Performance

Avoid adding libraries or effects solely for visual novelty.

Prioritize:

-   Fast loading
-   Optimized images
-   Minimal unnecessary JavaScript
-   Efficient animations
-   Good mobile performance

A beautiful website that feels slow is not a polished website.

------------------------------------------------------------------------

# 26. Design System Consistency

Create or refine a consistent design system covering:

### Colors

-   Background
-   Surface
-   Text
-   Muted text
-   Border
-   Primary
-   Secondary
-   Semantic states

### Typography

-   Font family
-   Scale
-   Weight
-   Line height

### Spacing

Use a consistent spacing scale rather than arbitrary values everywhere.

### Components

Standardize:

-   Buttons
-   Inputs
-   Cards
-   Tables
-   Navigation
-   Modals
-   Badges
-   Alerts
-   Tabs

Consistency makes the interface feel engineered rather than generated.

------------------------------------------------------------------------

# 27. The "Real Product" Test

After implementation, inspect every major page and ask:

### Within 5 seconds, can a new user understand:

-   What this product is?
-   Who it is for?
-   What problem it solves?
-   What they can do?
-   What action they should take next?

If not, improve the information hierarchy.

------------------------------------------------------------------------

# 29. Implementation Instructions for Antigravity

When using this document to refine an existing project:

## Step 1 --- Audit

Inspect the existing application before changing it.

Identify the **10 biggest issues** that make it look generic or
AI-generated.

## Step 2 --- Prioritize

Fix issues in this order:

1.  Information hierarchy
2.  Typography
3.  Layout
4.  Real product content
5.  Navigation
6.  Component consistency
7.  Interaction states
8.  Responsive behavior
9.  Accessibility
10. Decorative refinement

## Step 3 --- Implement

Modify the existing codebase.

**Do not rebuild the application unnecessarily.**

Preserve:

-   Existing functionality
-   Routes
-   APIs
-   Authentication
-   Database behavior
-   Business logic
-   Existing useful components

## Step 4 --- Remove Before Adding

Before introducing a new visual element, ask:

> "Does the website actually need this?"

If not, remove it.

The goal is **not to add more design**.

The goal is to make the existing design **more intentional**.

## Step 5 --- Final Review

Review every major screen on:

-   Desktop
-   Tablet
-   Mobile

Check:

-   Visual hierarchy
-   Spacing
-   Typography
-   Consistency
-   Accessibility
-   Performance
-   Realistic content
-   Interaction states

------------------------------------------------------------------------

# 30. Golden Rules

Keep these rules in mind throughout the entire implementation:

> **Real product \> decorative mockup**

> **Specific copy \> generic marketing**

> **Usability \> visual effects**

> **Consistency \> novelty**

> **Information hierarchy \> empty space**

> **Subtle interaction \> excessive animation**

> **Authenticity \> artificial "wow"**

> **Purposeful design \> trendy design**

> **Remove unnecessary elements before adding new ones.**

> **When unsure whether to add an effect, don't add it.**

------------------------------------------------------------------------

# Final Objective

The finished website should make a visitor think:

> **"This looks like a real product made by a serious team."**

Not:

> **"This looks like an AI-generated website."**

The goal is **not anti-modern design**.

The goal is:

## Modern + Intentional + Usable + Credible + Human
